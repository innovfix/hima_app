Direct answer to "can we fully fix all this without touching the backend?" — No. Of 16 bugs, only 1 can be 100% closed from Android alone. The rest either need the backend team, or need an action outside the Android code repo (like rotating a key in a vendor dashboard).

BUG-001 S1 Critical Fix: Android + Server OTP is verified only on the Android client — /login accepts any code

Where: VerifyOTPActivity.kt:138–156 (client OTP compare)  ·  ApiManager.kt:1753–1759 (/login)
What: The client compares the entered OTP with the one it generated locally, then calls /login with hard-coded code="0", code_verifier="0". The server does not re-validate the OTP. A backdoor OTP "011011" is hard-coded in the client.
// VerifyOTPActivity.kt:143
if (enteredOTP == otp.toString() || enteredOTP == "011011") {
    login(mobileNumber)          // → viewmodel.login(mobile, "0", "0")
}
Proof (no SMS ever sent):
$ curl -X POST https://demohima.himaapp.in/api/auth/login \
       -d "mobile=9876543210&code=0&code_verifier=0"

HTTP/1.1 200 OK
{ "success":true, "registered":true,
  "token":"eyJ0eXAiOiJKV1Qi...<valid JWT>",
  "data":{"id":456976, "mobile":"9876543210", ... } }
Impact: Complete account takeover of any user given only their phone number.
Android side (do now): Delete the "011011" branch at VerifyOTPActivity.kt:143. Stop generating the OTP client-side. Keep calling /login with the real user-entered OTP.
Server side (required to actually close the bug): Generate OTP server-side, store hashed with ≤5-min TTL + attempt counter, validate it in /login. Until this is done, the vulnerability is OPEN regardless of Android changes — an attacker uses curl, not your app.

BUG-002 S1 Critical Fix: Server only IDOR on /userdetails — any logged-in user can read every other user's profile

What: The server reads user_id from the request body instead of the JWT sub claim. Swapping user_id returns any user's data.
Proof:
$ curl -X POST .../userdetails \
       -H "Authorization: Bearer <my-token, sub=456976>" \
       -d "user_id=456975"

{ "data":{ "id":456975, "name":"NisdB403",
           "mobile":"8464643464",           // ← not my account
           "refer_code":"GZDB1289", ... } }
Impact: Mass PII leak. Any attacker can enumerate sequential user_ids and dump every user's mobile number + profile. DPDP-regulated data.
Server fix: Resolve user id from $request->user()->id (JWT sub). Stop accepting user_id from the body. Audit every other endpoint with the same pattern.
Android side: Nothing to do. Even if the app stopped sending user_id, an attacker with curl would still exploit the server.

BUG-003 S1 Critical Fix: Server only CORS reflects any Origin with Allow-Credentials: true

Proof:
$ curl -i -X OPTIONS .../login -H "Origin: https://evil.com"

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://evil.com        ← reflected!
Access-Control-Allow-Credentials: true
Impact: Any site the victim visits can call the API in their browser session and exfiltrate JWTs (combined with BUG-001).
Server fix: Whitelist allowed origins in Laravel CORS config. Don't reflect the request Origin. Drop Allow-Credentials unless strictly required.
Android side: Not applicable — mobile apps don't participate in CORS.

BUG-004 S1 Critical Fix: Server only No rate limiting on /send_otp or /login

Proof: 20 consecutive /send_otp in < 2 s, all returned HTTP 200 (each triggered a real SMS).
Impact: SMS-bombing any Indian mobile, cost abuse, brute-force window for OTP (after BUG-001 is fixed).
Server fix: Laravel throttle middleware. Per-mobile + per-IP (1/30s, 5/hr, 10/day). Per-mobile attempt cap on /login.
Android side: Nothing effective. A 30-second UI cooldown is cosmetic — attackers don't use your UI. Do it anyway for UX, not security.

BUG-005 S2 High Fix: Server only /send_otp returns HTTP 500 (HTML) for any invalid input

Proof:
$ curl -i -X POST .../send_otp       # missing body
HTTP/1.1 500 Internal Server Error
Content-Type: text/html
<!DOCTYPE html><title>Server Error</title>...
Server fix: Add a Laravel FormRequest validator returning JSON 400 (mirror what /login already does).
Android side: You already validate mobile client-side, so this rarely fires for your users. Ensure Retrofit doesn't crash on non-JSON responses — wrap in try/catch around response.body() and show a generic error.

BUG-006 S2 High Fix: Android + Server /send_otp accepts the OTP value from the client

Proof:
$ curl -X POST .../send_otp -d "mobile=9876543210&country_code=91&otp=-1"
{"success":true,"message":"OTP sent successfully."}

$ curl -X POST .../send_otp -d "mobile=9876543210&country_code=91&otp=<script>alert(1)</script>"
{"success":true,"message":"OTP sent successfully."}
Android side (do now): Remove the client-side OTP generation. Change Retrofit signature to drop the otp field. Files to edit: LoginViewModel.kt, ApiManager.kt, NewLoginActivity.kt. Must ship together with server change — flag behind a config.
Server fix: Stop accepting the otp field. Generate cryptographically-random 6-digit OTP server-side; return nothing sensitive to the client.

BUG-007 S2 High Fix: Server only /register does not require any proof of mobile ownership

Proof:
$ curl -X POST .../register \
       -d "mobile=9000000003&language=Tamil&avatar_id=21&gender=male"
{ "success":true, "message":"Registered successfully.", "token":"...", ... }
Server fix: After fixing BUG-001, require a single-use server-issued OTP token (≤5 min TTL) in /register that proves the mobile was just verified.
Android side: Once server exposes the new signed-OTP token, pass it through from the OTP verify step to register. No-op until server changes.

BUG-008 S2 High Fix: Server only JWT is valid for 90 days with no revocation path

Proof — decoded JWT payload:
{ "iss": "https://demohima.himaapp.in/api/auth/login",
  "iat": 1776761750, "exp": 1784537750,     //  exp-iat = 90 days
  "sub": "456976" }
Server fix: Short-lived access token (≤ 1 h) + refresh token with server-side rotation and revocation list. Add /logout that blacklists the jti.
Android side (supporting work): (1) Store the JWT in EncryptedSharedPreferences instead of plain prefs. (2) Implement a Retrofit Authenticator to refresh-on-401 once server exposes the refresh endpoint. (3) Call a real /logout from the logout button (today it only clears prefs).

BUG-009 S3 Medium Fix: Server only country_code=xyz accepted on /send_otp

$ curl -X POST .../send_otp -d "mobile=9876543210&country_code=xyz&otp=123456"
{"success":true,"message":"OTP sent successfully."}
Server fix: Strict integer validation + allow-list of supported country codes.
Android side: Already sends Int, so this never fires from the app. No change needed.

BUG-010 S3 Medium Fix: Server only HTTP 200 returned for business-logic failures

/register, /send_otp, /avatar_list etc. return HTTP 200 with {"success":false,...}. Inconsistent with /login.
Server fix: 4xx for validation / business failures. Never HTML.
Android side: Your code already checks response.body().success, so functionally fine. No change needed, but once server fixes this, some existing if (body?.success == false) branches can be simplified to rely on response.isSuccessful.

BUG-011 S3 Medium Fix: Server only /first_install leaks caller IP

{ "ip_address":"103.163.232.121", ... }
Server fix: Remove ip_address from the response.
Android side: The app already ignores this field. No change needed.

BUG-012 S3 Medium Fix: Server only Referral code not validated on /register

referred_by=INVALIDXYZ → account created, referral silently dropped.
Server fix: Reject unknown codes OR attribute + return the partner id. Either way, tell the client.
Android side: You can't verify codes without a lookup endpoint. If server adds /validate_referral, wire it into the "Enter referral" screen before calling /register.

BUG-013 S3 Medium Fix: Android + Server No payload size cap on /register

10 KB describe_yourself accepted. Combined with BUG-004 → DoS / DB bloat.
Android side (do now): 
// On every editable field in the signup flow
binding.etDescribeYourself.filters = arrayOf(InputFilter.LengthFilter(500))
binding.etName.filters             = arrayOf(InputFilter.LengthFilter(50))

<!-- XML equivalent -->
android:maxLength="500"
Server fix: Add max rules on the validator (describe_yourself ≤ 500, name ≤ 50, etc.). Real protection — attacker ignores your InputFilter.
