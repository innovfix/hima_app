1. Summary

Today I ran an API-automation pass of the Hima Android Male Transactions and Female Transactions screens, targeting the two transaction endpoints /transaction_list and /female_transaction. I ran the suite twice — first with only a male QA account (30 cases) to baseline the male endpoint, then expanded to both a male and a female QA account (45 cases) once a female test number was available. This dual-account run was the important one: it unlocked parts of the female endpoint that the ownership gate had previously hidden, and confirmed which bugs are shared across both endpoints versus male-only.

Across the 45 automated cases I uncovered 6 unique bugs (1 S1 Critical, 3 S2 High, 2 S3 Medium). I also performed on-device manual verification of both Android patches landed today (BUG-TX-004 and BUG-TX-007) on a real emulator session and confirmed they behave correctly. The headline is a critical IDOR on /transaction_list: any logged-in user can read any other user's complete financial history just by sending a different user_id in the POST body. Proof: male QA token (id 456976) fetched 272 rows belonging to female QA (id 456740) on demo, and separately 8,926 rows belonging to a female user (id 72530) on prod. The sibling /female_transaction endpoint already enforces the ownership check correctly — the fix is a copy-paste from that controller.

Branch status: I landed the two Android-side mitigations that were possible (nullable schema fields + error observer). Both compiled cleanly with ./gradlew :app:compileDevelopmentDebugKotlin → BUILD SUCCESSFUL, zero new warnings. The other four bugs are server-only — there is no client-side code change that closes them, because a curl user or patched APK bypasses any app guard. Those four are fully documented for the backend team with exact Laravel validator snippets. No push to main — pending senior review and on-device verification of the two Android patches.

Functional, pagination, boundary, negative, security (IDOR / auth / SQLi / gender-gate / cross-endpoint), HTTP-verb correctness, response-contract and performance p95 cases. Read-only suite — no transaction was created, no call placed, no coin deducted.

  • Exercised 2 endpoints: /transaction_list and /female_transaction, with BOTH a male-token and female-token context for cross-account / gender-gate coverage (cases prefixed TXX-*).
  • Confirmed CRITICAL IDOR on /transaction_list: the endpoint trusts the body user_id instead of deriving it from the JWT subject. Proven on both demo (male→female 456740, 272 rows) and prod (male→female 72530, 8,926 rows) — BUG-TX-001. The sibling /female_transaction correctly blocks this in both directions (TXX-01, TXX-02 passed), so the fix pattern already exists in the codebase.
  • Confirmed HTML 500 leak on limit=-1 on both endpoints (BUG-TX-004). Server returns the Laravel HTML error page instead of JSON. Reachable on the female endpoint only once we had a female token — this was a new dual-account finding.
  • Confirmed no server-side cap on limit on both endpoints (BUG-TX-005). limit=99999 returned 272 rows on the female endpoint and 272 rows on the male endpoint in a single response. Compound with BUG-TX-001 → a one-shot scrape of any user's full history.
  • Confirmed schema mismatch (BUG-TX-007): /transaction_list responses are missing user_name, call_type, duration, call_user_name — fields declared non-nullable in TransactionsResponse.kt. Today Gson silently fills with null; future Kotlin 1.9 upgrade makes this a hard crash on the Transactions screen.
  • Confirmed silent negative-offset coercion on both endpoints (BUG-TX-003). offset=-1 and offset=0 return identical first_id — server silently coerces instead of rejecting.
  • Confirmed HTML 302 fallback when Accept: application/json is absent (BUG-TX-002). Retrofit always sets this header so the shipping app is fine today — but non-Retrofit consumers / dropped-header interceptors will crash their JSON parser. Caught only when we bypassed the header explicitly.
  • Positive result: /female_transaction is the hardened reference. Ownership check fires bidirectionally (TXX-01, TXX-02), gender gate works (TXX-04), all 10 Kotlin fields are present (TXF-02), SQLi probes rejected early (TXF-08), tampered JWT rejected (TXF-15). Every shared bug (BUG-TX-003, 004, 005) has the same server-side validator fix that closes both endpoints in one change.

4. Client-Side Changes Landed Today

4.1 TransactionsResponse.kt — nullable schema + amount type (Partially fixed BUG-TX-007)

  • Changed 6 fields from non-null String to nullable String?: user_name, date, call_type, duration, call_user_name, payment_type. The server never sends these today — the old data class was lying to the compiler.
  • Changed amount: Int → amount: String?. The server returns a decimal-formatted string ("3.00"), not an integer. Gson previously silently coerced — a crash waiting to happen on any device where the coercion path differs.
  • Added a one-line comment explaining why amount is a string, so a future developer doesn't "fix" it back to Int.

Backend still required: the server should emit the documented keys (empty-string fallback) so the API contract is stable for any future consumer. Otherwise a third-party integration will run into the same surprise.

4.2 TransactionAdapter.kt — null-safe rendering (Partially fixed BUG-TX-007)

  • Replaced direct string-template use of transaction.call_user_name and transaction.duration with local vars that use .orEmpty() before interpolation. Same for transaction.date.
  • Conditional rendering: "$callType session with $callUserName" degrades to "$callType session" when callUserName is empty. "$dateText · $durationText" degrades to just dateText when duration is empty. No more literal "null" text visible on screen.
  • No behavioural change for rows where the fields ARE populated — tested via compile + static review; device verification pending.

4.3 TransactionsActivity.kt — error observer for non-JSON responses (Partially fixed BUG-TX-004)

  • Added an observer on transactionsViewModel.transactionsErrorLiveData — the ViewModel already posts to this LiveData on onFailure and onNoNetwork (see TransactionsViewModel.kt:36-42), but until today nobody was listening on the male screen. The female screen already had this observer (FemaleTransactionsActivity.kt:128-137) — I mirrored its logic.
  • On error, the observer shows a toast — "No internet connection" if error == DConstants.NO_NETWORK, otherwise "Please try again later" — AND displays the "No records" fallback view. This replaces today's silent-blank-screen behaviour when the server returns HTML 500 on limit=-1, HTML 302 without Accept:json, or any network failure.
  • Imports added: android.util.Log, android.widget.Toast, com.gmwapp.hima.constants.DConstants. No other file touched.

Backend still required: the server should not return HTML 500 at all (BUG-TX-004) and should never return HTML 302 for /api/* routes (BUG-TX-002). The client observer is a defensive UX fix — it makes the symptom less harmful, but the underlying server bug remains.

5. Documented-Only Bugs (backend fix required)

These bugs have no meaningful client-side mitigation — the root cause is on the server and any attacker bypasses client guards. They are captured in the API test report with repro steps, proofs, and recommended fixes for the backend team.

  • BUG-TX-001 — /transaction_list: derive user_id from JWT sub; ignore body user_id. The sibling /female_transaction already does this — copy that pattern. Suggested one-liner: abort_if($request->input('user_id') != $request->user()->id, 403);
  • BUG-TX-002 — force JSON 401 for request()->is('api/*') in Laravel's exception handler, regardless of the Accept header. Currently the web auth guard returns HTML 302 → /login which breaks any non-Retrofit client.
  • BUG-TX-003 — add 'offset' => 'nullable|integer|min:0' FormRequest validator on both /transaction_list and /female_transaction. Currently negative offsets are silently coerced to 0, enabling a subtle double-render bug if a client pagination miscomputes.
  • BUG-TX-005 — add 'limit' => 'nullable|integer|min:1|max:100' on both endpoints. Currently limit=99999 returns the full user history in one payload — exhausts DB connections and Gson parse memory. $data->take(min($limit, 100)) in the controller as a belt-and-braces second line of defence.

BUG-TX-004 and BUG-TX-007 also have backend counterparts (limit validator, and emit-all-keys for contract stability) — those are not duplicated here because they are documented under the "partially fixed" bugs in section 3.
