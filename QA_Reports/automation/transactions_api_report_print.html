TL;DR for the tech lead

I ran 45 API test cases against the two transaction endpoints. 35 passed and 10 failed. The failures map to 6 distinct bugs, 100% of which are fixable with code we own (the other are documented behaviour, no fix needed). One failure is CRITICAL: /transaction_list has an IDOR that leaks every user's full financial history to any authenticated user — the sibling /female_transaction endpoint already fixed this, so the patch is a copy-paste.

1. Executive summary

Coverage spans functional, pagination, boundary, negative, security (IDOR / auth / SQLi / tampered JWT), HTTP-verb correctness, response-contract and performance p95 categories. The female endpoint is the hardened reference: it passes all ownership, validation and gender-gate tests. The male endpoint is 8 years of drift behind it and accumulates most of the findings.

3. Bugs — plain-language breakdown (critical first)

CRITICAL BUG-TX-001 FIX: SERVER Male Transactions Security

/transaction_list — IDOR: male token reads FEMALE user's txns

What's wrongAny logged-in user can read ANY other user's complete transaction history (amount, payment_type, datetime) just by sending a different user_id in the request body.
Why it mattersCRITICAL. Financial-history privacy leak. Test proof: our male QA token (user_id=1125868) successfully fetched 8,926 transactions belonging to female user_id=72530. This affects every user on production right now. Under Indian DPDP / GDPR this is a reportable data-protection incident.
How to fixBackend: derive user_id from the JWT sub claim, ignore the value in the request body. The sibling endpoint /female_transaction already does this correctly — copy that pattern (`abort_if($request->input('user_id') != $request->user()->id, 403)`).

HIGH BUG-TX-005 FIX: SERVER Female Transactions Performance

/female_transaction — limit=99999 also uncapped?

What's wrongThere is no upper cap on the `limit` query parameter. A single request with limit=99999 returned 8,926 rows (~1.5 MB JSON) in our test — and the server happily served it.
Why it mattersHigh. Two attack surfaces: (1) DoS — a few thousand such requests exhaust MySQL connection pool and bandwidth; (2) Mobile OOM — if a patched APK sends limit=99999, Gson will blow up parsing on older Android devices. The Android app itself sends limit=10 (safe), so this is reachable via curl / patched APK only, but still must be enforced server-side.
How to fixBackend: add `'limit' => 'nullable|integer|min:1|max:100'` and cap in the controller: `->take(min($limit, 100))`.

HIGH BUG-TX-007 FIX: BOTH Male Transactions Contract

/transaction_list — response schema matches TransactionsResponse.kt

What's wrongThe Kotlin data class `TransactionsResponse` declares several fields as non-nullable (user_name, call_type, duration, call_user_name) but the server response does NOT include them.
Why it mattersHigh. This is a latent runtime crash waiting to trigger. Today Gson silently defaults missing non-null fields to null (which violates the Kotlin contract), but on Kotlin 1.9+ with strict null safety this will throw IllegalStateException at deserialisation — a blank transactions screen for every male user. Confirmed: our test fetched 5 rows and all 5 were missing those 4 keys.
How to fixTwo-part fix (defence in depth). Android: mark the fields nullable in TransactionsResponse.kt: `val user_name: String?`, `val call_type: String?`, `val duration: String?`, `val call_user_name: String?`. Backend: always emit the documented keys (empty string fallback) so the API contract is stable for any future consumers.

MEDIUM BUG-TX-003 FIX: SERVER Female Transactions Validation

/female_transaction — negative offset (silent coercion on female too?)

What's wrongNegative offset values (e.g. offset=-1) are silently coerced to 0 instead of being rejected.
Why it mattersMedium. A buggy client sending `offset = Math.max(0, page-limit)` with off-by-one math could re-render page 0 content and double up rows. Also inconsistent: the non-numeric user_id IS rejected cleanly, but negative offset is not. The same call with offset=-1 and offset=0 returned identical first_id=43261177 in our test, proving silent coercion.
How to fixBackend: add `'offset' => 'nullable|integer|min:0'` to the FormRequest validator and return 400 JSON on failure.
Server response observed{"neg_first": 7093032, "zero_first": 7093032, "neg_success": true}
MEDIUM BUG-TX-002 FIX: SERVER Male Transactions Contract

/transaction_list — no-auth without Accept:json returns HTML 302

What's wrongWhen a client calls the API without an `Accept: application/json` header, the server responds with HTML 302 → /login instead of a JSON 401.
Why it mattersMedium. The Android app is fine today (Retrofit sets Accept:json), but any third-party consumer, a misconfigured OkHttp interceptor, or a future non-Retrofit client will crash its JSON parser. Also a subtle consistency smell — /api/* routes shouldn't do web-auth redirects.
How to fixBackend: in Laravel's exception handler, force JSON 401 when the request path starts with `api/` regardless of Accept header.

5. Methodology

  • Authenticated tests use a real JWT obtained via /login for QA mobile 9876543210.
  • Read-only suite — no transaction was created or mutated on any account.
  • IDOR probes use a known real female account id (72530) as the foreign user_id. Test was read-only: no data was altered on that account.
  • Requests are spaced 150 ms apart to avoid triggering throttle middleware.
  • Contract checks validate that server responses contain every field the Kotlin data classes declare as non-null — a mismatch would crash the Android client at deserialization.
  • p95 performance budget: 2.0 s per request (stricter than the 8 s used for voice uploads).
  • One female-side contract test (TXF-07) could not be fully exercised because the ownership guard (correctly) blocks a male token — re-run with a real female QA account when one is provisioned.
