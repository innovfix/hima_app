01 Executive summary

For the tech lead — one paragraph

Automated API tests ran 45 checks against the two transaction endpoints with both a male and a female logged-in account. 35 passed and 10 failed. Failures map to 6 distinct bugs, 100% fixable with code we own. One is CRITICAL: /transaction_list exposes any user's financial history to any authenticated caller. The sibling /female_transaction endpoint already enforces the right check — the fix is a copy-paste.

Coverage spans functional, pagination, boundary, negative, security (IDOR, auth, SQLi, gender-gate, cross-endpoint), HTTP-verb correctness, response-contract and performance p95 categories. The female endpoint is the hardened reference — nearly every failure is on the male endpoint or shared across both.

BUG-TX-001 CRITICAL Fix: SERVER Male Transactions

/transaction_list — IDOR: male token reads FEMALE user's txns

What's wrongAny logged-in user can read any other user's complete transaction history (amount, payment_type, datetime) by sending a different user_id in the request body on /transaction_list.
Why it mattersCRITICAL. Financial-history privacy breach across all users. Test proof: male QA token (id 456976) fetched 272 rows belonging to female QA account (id 456740) on demo — same pattern confirmed on prod (8,926 rows of user 72530). Reportable under DPDP / GDPR.
How to fixBackend: derive user_id from the JWT sub claim, ignore the body value. The sibling /female_transaction already does this — copy that pattern.

BUG-TX-004 HIGH Fix: BOTH Female Transactions

/female_transaction — negative limit (HTML 500 leak on female too?)

What's wrongSending limit=-1 to either endpoint returns HTTP 500 with the Laravel HTML error page instead of a JSON error. Confirmed on BOTH /transaction_list and /female_transaction.
Why it mattersHigh. Breaks the Android client (it can't parse HTML as JSON → blank screen with no feedback). Information-disclosure risk if APP_DEBUG=true on prod.
How to fixAndroid: DONE — TransactionsActivity now observes errorLiveData and shows a toast. FemaleTransactionsActivity already had this. Backend: add 'limit' => 'integer|min:1|max:100' validator — one change protects both endpoints.

BUG-TX-005 HIGH Fix: SERVER Female Transactions

/female_transaction — limit=99999 also uncapped?

What's wrongNeither endpoint caps the `limit` parameter. limit=99999 returns every row in one response — 272 on demo, 8,926 on prod.
Why it mattersHigh. Two attack surfaces: DoS (a few thousand requests exhaust MySQL connections + bandwidth) and mobile OOM (Gson blows up parsing on older devices). Confirmed on BOTH endpoints.
How to fixBackend: add 'limit' => 'nullable|integer|min:1|max:100' validator and enforce the cap server-side. One validator protects both endpoints.

BUG-TX-007 HIGH Fix: BOTH Male Transactions

/transaction_list — response schema matches TransactionsResponse.kt

What's wrongTransactionsResponse.kt originally declared user_name, call_type, duration, call_user_name as non-nullable Kotlin Strings, but the server never sends them. Confirmed by TXM-02 — 5 rows inspected, all 4 fields missing.
Why it mattersHigh (latent). Today Gson silently defaults to null, violating Kotlin's null contract. On a Kotlin 1.9+ upgrade with strict null safety the Transactions screen crashes on first deserialize.

BUG-TX-003 MEDIUM Fix: SERVER Female Transactions

/female_transaction — negative offset (silent coercion on female too?)

What's wrongNegative offset values (offset=-1) are silently coerced to 0 on BOTH /transaction_list AND /female_transaction instead of being rejected.
Why it mattersMedium. A client with off-by-one pagination math can double-render rows without detection. Confirmed on both endpoints: first_id with offset=-1 equals first_id with offset=0.
How to fixBackend: add 'offset' => 'nullable|integer|min:0' validator on both endpoints.

BUG-TX-002 MEDIUM Fix: SERVER Male Transactions

/transaction_list — no-auth without Accept:json returns HTML 302

What's wrongWhen a client hits /transaction_list without Accept:application/json, the server responds with HTML 302 → /login instead of a JSON 401.
Why it mattersMedium. Retrofit sets Accept:json so the Android app is fine today, but any third-party client or misconfigured interceptor crashes its JSON parser against the HTML response.
How to fixBackend: force JSON 401 for request()->is('api/*') in Laravel's exception handler.

05 Methodology

  • Both accounts authenticated via /login with QA backdoor OTP 011011.
  • Male account: 9876543210 → id 456976 · Female account: 9120444444 → id 456740.
  • Read-only suite — no call, recharge, gift, profile change or transaction was created on any account.
  • Cross-account (TXX-*) cases use the other account's id to probe ownership / gender enforcement.
  • 150 ms inter-request delay to avoid throttle middleware.
  • Contract checks validate that response rows contain every field the Kotlin data class declares.
  • p95 performance budget: 2.0 s per request.
  • Manual on-device verification of the Android patches (BUG-TX-004, BUG-TX-007) is performed by Perumal — not by the automation script.

  3. Next sprint: Force JSON-only responses for /api/* routes (BUG-TX-002). Contract cleanup.
