Headline findings

  • BUG-TX-001 · CRITICAL IDOR on /transaction_list, confirmed on demo AND prod: the male QA token (id=456976) fetched the female QA account's (456740) full transaction history (272 rows on demo). The sibling /female_transaction correctly blocks this in both directions (TXX-01, TXX-02 passed).
  • BUG-TX-004 · 500 HTML leak: limit=-1 on /transaction_list returns HTML 500. Android side already patched to observe error state — server validator still needed.
  • BUG-TX-005 · No pagination cap: limit=99999 returns the entire history on /transaction_list. We also test if the female endpoint has the same weakness (TXF-11).
  • BUG-TX-007 · Schema mismatch: /transaction_list still omits documented Kotlin fields. Android already patched (nullable). Server should emit them for contract stability.
  • Design quirk (TXX-05): /transaction_list has no gender gate — a female can fetch her own data through it. That's why the IDOR exposes female data too. A single ownership-binding fix closes both directions.

BUG-TX-001 critical FIX · SERVER /transaction_list — IDOR: male token reads FEMALE user's txns

Screen: Male Transactions · Category: Security
Why it matters: POST /transaction_list trusts the body `user_id` field and does NOT verify it matches the JWT `sub`. Any authenticated user — male or female — can enumerate every other user's full financial history (amount, datetime, type, payment_type). The sibling endpoint /female_transaction enforces this correctly on both sides — transaction_list was missed. Confirmed twice: prod (male→female 72530, 8926 rows) and demo (male→female 456740, 272 rows).
Android side: Stop sending `user_id` in the POST body (derive from JWT) — client fix alone does nothing because a patched APK / curl still sends it.
Server side: REQUIRED. In the controller: `$uid = $request->user()->id;` and ignore `$request->input('user_id')`. Or add a guard: `abort_if($request->input('user_id') != $request->user()->id, 403);` matching the logic already present in /female_transaction.

BUG-TX-002 medium FIX · SERVER /transaction_list — no-auth without Accept:json returns HTML 302

Screen: Male Transactions · Category: Contract
Why it matters: Without `Accept: application/json`, the API returns HTML 302 → /login (Laravel web-auth fallback). Retrofit sets Accept:json so the Android app is fine — but any third-party consumer, or a mis-configured OkHttp interceptor that drops the Accept header, will crash its JSON parser.

Notes / methodology

  • Both accounts authenticated via /login using the QA backdoor OTP 011011.
  • Male account: 9876543210 → id=456976. Female account: 9120444444 → id=456740.
  • Read-only suite — no transaction, call, recharge, gift or profile change is created. No clean-up needed.
  • Cross-account (TXX-*) cases use the other account's id to probe ownership/gender enforcement. These are the tests we couldn't run in the first sprint because we only had a male token.
  • 150 ms inter-request delay to avoid throttle middleware.
  • Contract checks validate each row has every field declared in the Kotlin data class. Missing non-null fields crash Android Gson.
  • Manual on-device verification of the Android patches (BUG-TX-004, BUG-TX-007) is performed by Perumal — see device-test notes in the PDF.
