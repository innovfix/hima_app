## Current highest-severity rollup

The linked checkpoints contain evidence and exact behavior. This rollup is intentionally concise.

### Authentication and account integrity

- Android's logged-out entry surface (`NewLoginActivity`, reached from the launcher `SplashScreenActivity`) and the legacy `LoginActivity`/`VerifyOTPActivity` path generate/verify OTP locally and contain a bypass; backend login can issue a 90-day JWT from a mobile number without server-verified OTP ownership, and registration also mints the same long-lived token class. Critical account takeover path.
- Public registration does not prove mobile ownership.
- Live `users.mobile`, `name`, and `refer_code` are non-unique. Read-only aggregates found 1,575 duplicate-mobile groups, 15,709 duplicate-name groups, and 946 duplicate-referral-code groups.
- Registration can save a new duplicate-mobile row and then mint a JWT for an older arbitrary matching row because it re-queries with unordered `first()`.
- Multiple profile/voice/token/version endpoints use body user IDs instead of the JWT subject, enabling cross-account reads and writes.
- FCM token registration is ownership-weak and multi-path: `send_fcm_token` trusts the submitted `user_id`; login/Main use Retrofit, cold start uses both direct OkHttp and retrying WorkManager, and `onNewToken` replaces the same per-user registration work. Logout's exact-token invalidation is JWT-bound, but logout does not cancel old registration work and that worker does not re-check the active account. A delayed retry can therefore rebind the token after logout or steal it back from a newly logged-in account. Both registration and invalidation workers persist captured bearer tokens in WorkManager input.
- JWT logout does not revoke the 90-day token; account deletion is a ticket rather than deletion.

### Backend and production architecture

- The live authentication controller is approximately 24.6K lines and route authentication is split between route groups and a controller constructor except-list, producing many public high-impact endpoints.
- Live route listing is broken by a missing controller, weakening operational inspection.
- Socket.IO has no JWT authentication and trusts client-provided identities for chat/presence operations.
- app-3 has read/write DB splitting while app-1/app-2 primarily read the primary, creating node-dependent stale-read behavior behind the load balancer.
- Scheduler runs on app-1 and app-2; shared Redis locks cover some, not all, duplicate-execution risks.
- Media replication is asymmetric: app-1/app-2 bidirectionally mirror public media with `delete=false`, app-1 forwards to app-3, app-3 is outside the reverse mirror, and app-3 now carries materially more media than the other nodes. Uploads and reads are node-dependent; deletes can be restored by a surviving mirror copy and do not constitute a cluster purge.
- CORS effectively allows all origins with credentials.

### Calls, signaling, and money

- Main call settlement authorizes caller-supplied payer ID rather than JWT subject, accepts client timestamps, claims the call before money movement, and performs balances/ledgers/bonuses/referrals outside one transaction.
- Parallel call rows can debit from the same old payer balance and credit multiple creators while only one deduction survives.
- The live `every_min_update_connected_call` route is repeatable, non-idempotent, can drive payer coins negative, and uses inconsistent legacy rates.
- `female_call_attend` lets any authenticated account turn another user's ring/dead row into connected/billable state.
- Current Android source has both connecting screens call `call_ring_heartbeat` every 2.5 seconds through `CallAliveChecker.sendRingHeartbeat`, but no live backend route/controller or cached route exists on app-1, app-2, or app-3. In any build containing this source, the helper creates a fresh thread and `OkHttpClient` each tick, adding client/network churn while leaving server ring state unchanged. Installation of this exact source in the current production user build was not independently verified.
- Public `send-fcm-notification` permits arbitrary call signaling/state mutation, channel corruption, push delivery, and returns the receiver's raw FCM token.
- Public Agora token minting signs attacker-chosen publisher tokens for attacker-chosen channels and expiry. Channels are predictable or carried through the public relay.
- Caller-controlled `call_switch=1` can create an unowned synthetic switch row with no parent-call proof, bypass phantom/income guards, and mint creator payout against an arbitrary funded male.
- The public orphan cron is live in `enforce` mode. Calling it can trigger settlement and FCM; winning its shared minute lock can also starve the scheduler.
- Android business-failure responses are often HTTP 200 and ignored. The settlement worker marks any 2xx as success and uses `Result.failure`, not retry, for transient failures.
- Live `refer_bonus` has no logical uniqueness. Aggregate inspection found 23 duplicate reward groups: 21 five-minute and two ten-minute duplicates.
- A live snapshot found four random calls still open beyond 60 minutes; this is not proof each was a ghost, but shows recovery does not guarantee closure.
- Live call history is an authenticated cross-account IDOR: caller-supplied identity exposes another account's counterpart history, creator income, bonus, and favourite data. Missed-count and favourite endpoints also permit cross-account state mutation. Missed-call lifecycle uses two non-equivalent signals: ring creation increments `users.missed_calls` when the creator is not busy, while the Recent/Missed badge polls open call rows newer than the seen marker. `missed_call_count` and `users.missed_calls` therefore drift by design, and auto-disable keys off the latter.
- Ratings are not bound to the JWT or a completed call; any authenticated account can impersonate a rater and submit unlimited analytics-poisoning records.
- Ring cancellation/rejection durability varies by UI surface. System Telecom rejection uses only the public FCM relay, male full-screen rejection lacks the female path's durable worker, and caller cancel/timeouts have no durable retry.
- Terminal FCM mutation selects the newest row for a user pair rather than the signaled channel, so one parallel call can close a different row. Accept validation also varies across full-screen, notification, and Telecom surfaces.
- History search/sort/pagination operate only after a newest-500-row cap, making older results unreachable while totals can imply otherwise. Live favourite data already contains 614 duplicate pairs and 742 excess rows.

### Wallet and payment gateways

- Only PhonePe and Cashfree are currently selected by normal production data: 972,632 versus 590,123 users on the read-only replica, matching the executable registration/login/Android routing logic and live package catalogs. Google Play, Razorpay, and EKQR branches exist in Android but are currently unassigned, not normal active checkout paths.
- Public `try_coins` plus public `add_coins` form a repeatable payment-free coin mint. They are also the real dormant Google Play completion contract, which contains no Play receipt/token/provider order proof and consumes purchases before server credit without durable recovery.
- Public `razorpay_add_coins` credits any chosen user/package immediately with no payment proof. It has no active Android caller, but remains a live server-exposed mint capability.
- PhonePe is active, but the Android compatibility call returns success without credit. The every-minute checker permanently marks any non-completed order checked after only one minute, so later completion depends entirely on the webhook. Webhook/cron/multi-node/public-route races are not protected by an in-transaction payment row lock.
- Cashfree is active and its row-lock/idempotency/atomic credit path is materially stronger. However, its public unsigned webhook deliberately trusts the payload when the provider verification API errors, even with the live verification mode set to `enforce`.
- The current Razorpay link branch stores no local order and has no compatible HIMA callback: the deployed webhook expects a different reference format, while the callback goes to another domain. The EKQR webhook is unsigned and calls `add_coins` without required fields. Both paths are currently unassigned but would be broken/high-risk if enabled.
- The deployed payment “success” page always displays success and performs no verification or credit. Standalone legacy webhook/source files match Git on all three nodes; deployment is not treated as runtime use.
- Cashfree autopay is live only for Hindi and Punjabi. External mandate creation occurs before the one local per-user row is persisted and is not serialized. Re-initiation overwrites the only stored provider ID, leaving prior mandates/event streams without a user mapping.
- Live HMAC-verified events include 54 unmatched HIMA payment successes, eight at ₹299. Seven of the ₹299 provider IDs are recoverable from earlier event history, but the webhook does not use that mapping; its unknown-event branch records “processed” and cannot credit. No scheduled payment-credit reconciliation exists.
- Autopay cancellation ignores a `false` provider-cancel result, marks the local row cancelled, and tells Android success. Terminal rows are then excluded from status polling and the unscheduled reconciliation command. A still-live old mandate can keep charging while re-subscription overwrites its ID and future events go unmatched.
- The Android initiate contract cannot deserialize/act on the backend's `already_active` response. A protected active or in-progress mandate is displayed as “Couldn't start autopay,” encouraging retries.
- Trial eligibility is inconsistent in executable code: the response's launch-date/zero-coin/never-active rule is not used by current plan-selection surfaces, and the backend accepts `trial_new` for any never-active user. Old or coin-bearing never-subscribers can still receive the ₹1 path.
- Subscription webhook HMAC verification is sound, but concurrent idempotency claiming is not atomic. Its renewal credit reads and saves `users.coins` without a user-row lock and does not increment `total_coins`; concurrent renewal/daily-claim/recharge/call/gift writers can overwrite a balance change while event and ledger records still commit. Several failure/cancel pushes also run inside the DB transaction, so duplicate credits, lost balance updates, and long lock holds remain possible. (Corrected against current repository source during strong-model review on 2026-07-15; the SQL `increment()` path belongs to ordinary Cashfree PG, not subscription renewal.)
- Daily subscriber claims have a real per-day unique key but use an unlocked balance update, omit `total_coins`, and create no general transaction ledger row. The separate active welcome-gift API trusts body user IDs and has no transactional/unique claim marker.
- Creator bank withdrawal is an active, high-volume path: live production recorded 96,546 bank rows in the latest 30-day IST window. UPI has substantial historical rows but zero in that window and is hidden/rejected by the live `upi=0` switch, so it is currently dormant rather than dead.
- Active bank payout calls Cashfree while holding the MySQL user row lock but persists no local idempotent intent before the provider request. A provider-accepted payout followed by timeout, lost response, insert failure, or commit failure rolls back the local balance/row while money may already be moving; a retry gets a new transfer identifier and can pay twice. The current code does retry only on `beneficiary_not_found` with case-variant `beneId` candidates, but that narrow fallback does not close the unknown-outcome hole.
- The live-enforced public Cashfree payout webhook rejects only a present-but-wrong signature; an omitted signature bypasses HMAC verification and can refund/mark reversed a paid withdrawal when a matching transfer ID is supplied. Its transfer lookup is an unindexed scan over roughly 620.5K rows.
- Withdrawal reconciliation is genuinely scheduled every minute on app-1 and app-2, not app-3, through the public load-balanced URL. Locks are node-local and phase-1 refunds are unlocked/non-transactional. Phase 2 repeatedly selects only the newest 25 paid rows; live data contains 6,218 rows in its 48-hour window, so most can be permanently starved from reversal checks.
- Strong-model withdrawal review on 2026-07-15 confirmed that `WITHDRAWAL_RETRY_SHADOW` is classification/logging only. Even for the three whitelisted transient status codes it logs `would=RETRY` and then executes the existing status-2 refund path; automatic payout retry, deterministic retry identity, and persist-before-provider retry intent are not implemented.
- Bank verification is not serialized, permits reuse of the same bank account across users, and logs provider authorization material/PII. `bank_updates` and `withdrawal_bank_details` lack `user_id` indexes; the latter is one overwriteable row per user, not a per-withdrawal account snapshot. The dormant UPI setup can report success after regex-only fallback without creating/persisting the Cashfree beneficiary ID later required for payout.
- Male transaction history is JWT-required but trusts an arbitrary body user ID, exposing another account's recharge/debit/gift/referral history and matched call partner details. It intentionally hides call deductions below 10 coins; 1,987 of 4,816 call deductions in the latest-10,000 ledger sample were hidden, so displayed balance and visible history do not reconcile by design.
- Creator history ignores the exact non-null `transactions.call_id` present on every recent sampled `call_income` row. Every ten-row page instead loads that creator's entire completed-call history, fetches all distinct caller names, and performs nested timestamp matching in PHP. At roughly 73.4M transactions and 41.0M calls this is an active correctness, latency, and memory risk.
- Both Android history screens use fragile offset paging: failed pages are skipped, totals/end-of-list are ignored, initial loading is not guarded against a second request, and creator server errors are rendered as “no records.” The backend filesorts by `datetime` because no `(user_id,datetime)` transaction index exists and recomputes an unused total each page.
- In-call gifts are active but the JWT is not bound to the requested sender; any authenticated account can spend another user's coins and credit a chosen female. Sender debit, receiver income, and two ledger rows are independent unlocked writes with no idempotency, allowing partial, lost, or repeated transfers. Android's active sender-history rendering also prefixes a stored negative gift value with another minus sign (`--20`).
- The live admin withdrawal page is visible to all admin/support users and allows selecting every status. Bulk cancel can move an already-paid row to cancelled and refund gross balance; bulk Paid can mark a provider-pending/failing row paid without verification. Neither path row-locks its state check, so concurrent admin/cron/webhook actions can refund twice.
- Urgent manual credit intentionally refunds before Cashfree is terminal and relies on later human clawback; production has three manual-credit markers and two detected double pays. Its pre-transaction checks are not locked, so concurrent submissions can duplicate the refund. The alert count has no acknowledgement lifecycle.
- The manual withdrawal XLS importer marks `failed` as status 2 without refunding creator balance and can move an already-cancelled/refunded row back to paid. It bypasses the live provider/hold guard and is partially applied row-by-row even when the overall upload reports errors.
- Manual user-wallet changes are a separate inconsistency class. The live user-edit form visibly posts editable `balance`, `coins`, and `total_coins`, and `users.update` overwrites them with no validation or ledger row. Active `addCoins`, `addBalance`, and `femalereports/add-bonus` helpers are unlocked save-then-ledger writes with no surrounding transaction/idempotency key, permitting wallet-only partial commits, lost concurrent updates, duplicate retries, and partially applied bonus batches. `addCoins` additionally labels an admin grant as ordinary `add_coins`/`Credit` with no amount/provider/admin marker; live offer, segmentation, notification, analytics, and invoice consumers can therefore misclassify the grantee as a payer and count/render a null-value recharge.

### Chat, friends, and blocking

- The live Socket.IO server has no authenticated socket identity. Clients can claim arbitrary users, join predictable personal/chat rooms, impersonate sends, forge reactions/read receipts, and tombstone messages using body-supplied identities.
- The exact audited Node source is running on all three nodes. Port 3003 listens on every interface and returned HTTP 200 directly on each public node address, so unauthenticated diagnostic/history/list/verify endpoints and realtime impersonation are internet-reachable rather than private-network-only.
- Normal Laravel chat routes require a JWT but frequently trust a different body user ID. Live code permits cross-account chat/friend history and list disclosure plus cross-account read-state, unified block/unblock, reaction, attachment, message, unread, and OneSignal notification mutations.
- `fallback_send_message` does not bind its sender to the JWT and omits the canonical friends/autopay send decision. It can impersonate another account, bypass the advertised chat gate, persist state, and trigger an outward push.
- `chat_gate_status` computes the send decision and then ignores it. Autopay-language users appear unlocked without subscription validation, non-autopay users can remain locked when the kill-switch is off, and REST/Socket permissions diverge.
- Android sends no socket authentication proof or durable client message/idempotency key. Acknowledgements are matched by payload, generic errors are ambiguous with concurrent sends, process death loses pending correlation, and retry after an unknown commit can duplicate messages.
- Chat push delivery is non-durable: the offline socket bridge is launched after message commit without delaying delivery acknowledgement; Laravel retries only connection exceptions in-request, always returns top-level success, and Node can log `onesignal_success=false` as success. REST fallback posts once with retries disabled. Neither path has a durable queue or post-commit reconciliation, so a push can be lost after the message row commits.
- Android emits typing/status events for which the audited server has no handlers. Realtime flows use 256-item `DROP_OLDEST` buffers, and reactions still narrow a `Long` message ID to `Int`.
- Live chat scale is approximately 10.3M estimated `chat_messages`, 2.10M `friend_requests`, and 1.75M `active_chats`. Chat lists do unbounded/N+1 work before PHP pagination. Friend and both block pair tables lack uniqueness; friend requests also lack a pair/status composite index.
- Attachment validation accepts allowed MIME *or* allowed extension, while socket and REST send paths lack consistent type/length/URL ownership constraints. Public orphan uploads, filter bypass, and untrusted attachment URLs are possible.
- Friend rejection status is reversed between Android surfaces. The status-2 path saves the rejection and then calls a nonexistent helper, returning HTTP 500 after persistence; the status-3 path is counted as Sent and sends no rejection push. Live status distribution is 193 rejected versus 177,625 cancelled rows.
- Node auto-seeded friend requests call a route whose controller method is missing in both Git and live production. The production notification flag is on, so pending requests/messages can succeed without alerting recipients.
- Friend push types do not match Android's refresh types, and the integrated Friends/Creator hubs do not register the advertised broadcast. Visible badges can remain stale even when a banner/click route works.
- Favourite add/remove/check and the `fav=1` list source trust body user IDs rather than the JWT subject. Any authenticated account can alter or inspect another account's favourites; the live table already contains 614 duplicate pairs and 742 excess rows.

### Creator lifecycle and administration

- Active creator availability and DND APIs trust requested user IDs rather than the JWT subject. Any authenticated account can alter another creator's availability/DND; `female_status_list` is also a cross-account creator financial/KYC PII disclosure.
- Android can clear DND locally before the server clear succeeds, producing an active “online but unavailable” state until server DND expires.
- Android checks local DND before payload classification in both FCM and OneSignal handlers, so DND suppresses all incoming pushes—not only calls or chat—until local expiry/clear.
- Public every-minute creator cron and dual-node notification scheduling mutate availability and send outward notifications without a cross-node claim. Creator-online check/send/log is non-atomic: simultaneous nodes can send duplicates, while the queued processor deletes work after a caught provider exception and can lose a failed notification instead of retrying it.
- Creator availability, missed-call badges, and auto-disable are three different counters: `calls_status_update` / `toggle_dnd` manage availability and DND, `creator_online_queue` feeds the online-push cron, `missed_call_count` counts open rows older than 50 seconds for the badge, and `cron_jobs` disables creators when `users.missed_calls >= 5` with `busy = 0`. Auto-disable is capped at 500 eligible creators per invocation, ordered by highest missed count.
- Production `voice_verify_mode` changed to `enforce` at 2026-07-15 15:40:01 IST. Inline AI verification is therefore active on app-1/app-2: qualifying reliable female scores can auto-approve because auto-approve is on, while low-confidence cases remain pending because auto-reject is off. Manual verification remains the fallback for review/error cases and all app-3 uploads. The batch Gemini command is unscheduled. If auto-reject is enabled later, the advertised “auto reject” behavior actually converts low-female-confidence applicants into verified male accounts.
- Creator verification routes have no role-level middleware. Global guards exclude view-only role 3 and moderator role 4, but superadmin, admin, and support role 2 can change creator status and the voice-verification feature flag.
- app-3 is missing `VoiceVerificationService.php` and runs an older verification controller without toggle/accuracy handlers or the 1,000-row query cap. With enforce mode now on, this is an active node-dependent onboarding failure: app-3 catches the missing-class error and leaves uploads pending while app-1/app-2 can score and auto-approve. Fresh retained app-3 failures were present through 2026-07-15 15:40:14 IST. The verified filter can attempt to hydrate an estimated 627K rows on app-3 while app-1/app-2 cap at 1,000.
- Moderation is the active warning engine (1,358 live rows through 2026-07-14). Every warning level-up also hard-deletes the warned creator/male user's entire chat history. Level mutation, push, multi-table deletion, counter consumption, and token invalidation are non-transactional; failures/retries and concurrent moderators can partially apply or over-escalate.
- General Creator Warnings lets support role 2 mutate restrictions. Its Level 4 path does not actually block the account, and levels can never be lowered, making its Level-0 reset branch unreachable for warned creators. Android silently renders warning API failures as “All Good.”
- The legacy warning engine remains directly executable with incompatible levels 0–5, while Android understands 0–4. It lacks durable manual-block state and can be undone by warning expiry. Production shows only two legacy rows from May 26 versus current moderation activity.
- `BlockedUsersController` conflates pair blocking with the global account `users.blocked` flag. Its unguarded bulk-unblock can clear a permanent moderation/manual block; support is hidden from the menu but can call the route directly.

### Tickets, public support, and AI

- Normal Android ticket creation/listing requires a JWT but trusts an arbitrary body user ID. Any authenticated account can create under or read another account's complete support history, replies, escalation details, and media URLs.
- Public GET/POST mobile endpoints and the public web form use only a mobile number. One endpoint discloses full ticket history and media URLs; public creation allows impersonation/uploads. Live duplicate-mobile ambiguity affects 1,575 values and 2,204 extra accounts.
- Ticket AI is active and synchronous: the row is saved before OpenRouter, both reply fields are written immediately on success, and OneSignal is sent in the same request. Provider retries can wait about 141 seconds and no idempotency key exists, so timeouts/retries can create duplicate tickets.
- Production-only `ticket_ai_account_context` is enabled. It transmits balances, lifetime income, recent recharge/withdrawal, seven-day calls, block state, language/gender/version, and ticket context to OpenRouter. The withdrawal lookup can scan the full ~611K-row table; a read-only measured no-match took about 1.7 seconds before the provider call.
- The every-minute delayed-reply command has no normal producer because current paths set `reply` and `ai_reply` together. Its two-to-ten-minute window left five February AI replies permanently stranded, and its multi-host check/save/push has no shared row claim.
- Public ticket media is node-local: ticket screenshots, ticket-reply attachments, review uploads, and other media land on the handling node's public disk, so file availability follows the asymmetric storage topology. Android logs complete ticket responses to Logcat and renders list errors as "No ticket raised," hiding auth/network/server failures.
- Android has no central media-cache invalidation. Chat temp files are normally deleted at terminal callbacks but teardown during delayed retry can orphan one; ticket submit copies are never explicitly deleted; the ticket pager uses `DiskCacheStrategy.ALL`. Separately, the retired trial-offer sheet has no UI caller but `MainActivity.onResume()` still performs its config/media prefetch. Production currently has one active Hindi video, identical on all three nodes.
- Support role 2 can directly access normal/AI ticket admin routes and invoke generation/provider tests. The visible AI-summary button calls a nonexistent route; its service also checks the key before loading config, so the feature is doubly broken.

### Reports, ratings, and testimonial rewards

- Post-call ratings are active at 1.66M rows but the endpoint accepts arbitrary rater/target IDs from any JWT, has no call proof/range validation/idempotency, and stores no call ID. Creator-ratings admin ranking is a hidden direct page with a temporary/filesort plan over recent calls and ratings.

- Upload Reviews is an active support-operated balance/coin credit surface. It uses ambiguous mobile lookup, has no reward uniqueness, uses unlocked balance updates, and stores unlimited-count 20 MB images node-locally. Deletion removes evidence but never reverses credit; 11 live `review_bonus` ledgers (₹69.99 plus 35 coins) lack surviving review rows.
- The custom app-rating dialog and feedback form have current Android callers but missing live API routes. Their historical rating data stops in March. The separate Google Play prompt route remains public but is currently off; its public event/check APIs permit arbitrary-user cooldown/rated-state forgery if used. ### Agency management and settlement

- Agency portal creator ownership is session-scoped, but login is unthrottled and does not regenerate the session. Portal views intentionally expose masked KYC/bank details plus balances, earnings, withdrawals, calls, and settlement figures despite stale comments saying earnings are hidden.
- All internal agency administration uses one shared HTTP Basic secret rather than named admin/role/2FA identity. It can expose full KYC/finance data, create agencies, assign creators, set commissions, and insert settlement payments with weak individual accountability.
