## Creator availability and DND: active production paths

- Female audio/video availability switches call the live JWT-protected `calls_status_update` API. The profile DND control uses `DndController`, which first best-effort disables both availability types and then calls the live `toggle_dnd` API. Backend call setup reads server DND state and rejects calls while receiver DND remains active.
- Android clears local DND immediately when a creator turns availability back on, then only best-effort clears server DND. If that request fails, the UI can show the creator online/DND-off while the server still rejects calls until DND expires. This is an active explanation for “online but nobody can call me.”
- Android enforces DND before classifying the payload in both `MyFirebaseMessagingService` and the OneSignal service extension. Active local DND therefore suppresses every incoming FCM/OneSignal notification, not only call rings; chat, friend, warning, availability-disable, and other pushes entering those handlers are also dropped until local DND expires or is cleared.
- `toggle_dnd`, `calls_status_update`, and `female_status_list` authenticate a JWT but do not bind their requested user ID to its subject. Any authenticated account can set another user's DND, turn another creator's audio/video availability on or off, and query the female-status response. The latter exposes creator mobile and financial/KYC fields, making it a high-severity cross-account PII IDOR.
- Turning availability on can enqueue and immediately send “creator online” notifications. Production currently has `creator_online_instant_enabled=true`.
- Each status-1 request creates a new open `calls_status_logs` row; status 0 closes only the newest open row. Repeated enables can therefore leave older open sessions permanently open. Live `calls_status_logs` is approximately 14.56M rows and has only `user_id` plus a separate `enabled_datetime` index for this lookup. The exact latest-open query uses the `user_id` index and then `Using where; Using filesort`.
- `creator_online_queue` uses `insertOrIgnore`, but production has no unique creator/type key—only a non-unique `(creator_id, created_at)` index—so concurrent duplicate enqueue is not ignored. A single processor run coalesces rows by `creator_id` and deletes all rows for every processed creator. Crucially, it also marks the creator processed and deletes those rows after a caught provider-send exception, so an ordinary send failure is dropped rather than retried. A process crash or queue-delete failure can leave rows for a later run, while simultaneous nodes can still select the same rows and send duplicates before either deletes them.

## Creator cron and online-notification runtime

- `/api/auth/cron_jobs` is a public GET excluded from the authentication constructor and is called every minute by the scheduler. It resets stale busy state, cleans random connections, auto-disables creators with excessive missed calls, closes status-log rows, sends disable pushes, sends scheduled screen notifications, maintains creator activity snapshots, and sends missed-call notifications.
- The scheduler runs on app-1 and app-2. `withoutOverlapping` is node-local for these executions, and the public load-balanced route has no whole-job shared claim. Two schedulers or an external caller can race the auto-disable selection/update and outward notifications. Screen-notification cache locking can also be node-specific.
- Auto-disable is keyed off `users.missed_calls >= 5` plus `busy = 0`, not the Recent/Missed badge query. The badge and the disable trigger are related but non-identical state machines. Each cron invocation handles at most 500 online eligible creators; already-offline counter reset is skipped from 22:00 through 00:59 IST. The selected users are ordered by highest `missed_calls`, so lower-count eligible creators can remain online for later runs during a backlog.
- `creator_active_monitor` currently has about 12.9K rows and only its primary key. Its “latest by created_at” query scans the table and filesorts; this grows into an avoidable periodic cost.
- Immediate creator-online sending performs check, provider send, and log insertion non-atomically. A simultaneous enable can pass the same pre-send rate check twice. A provider success followed by a logging failure leaves queue work that can resend; some provider failure response shapes may still be treated as success and drop the queue.
- `creators:process-notifications` is genuinely scheduled every 30 seconds on both scheduler nodes. Both can select the same queue rows, pass the same pre-send log checks, send twice, and then both delete. Conversely, a caught send exception is followed by queue deletion, so the same implementation can lose a notification rather than retry it. Production `creator_notification_logs` is approximately 58.75M rows; it has useful rate-limit indexes, but the cross-node claim/send sequence remains non-atomic. Repeat-caller recalculation is currently commented out, so that audience can become stale even though explicit opt-in preferences remain active.
- `cron_updates` is not scheduled, but its public route remains executable and mutating. Classify it as unscheduled public/manual capability, not dead code.

## Warning and moderation systems

### Runtime classification

- HIMA has three overlapping warning engines, not one:
  1. `ModerationWarningController` writes `moderation_warnings`, escalates creators through levels 1–4 and male users through 1–3, appends creator level changes to `creator_warning_logs`, sends OneSignal, and hard-deletes chat history on every level-up. This is **active production**.
  2. `CreatorWarningsController` is the general search/set-level admin page writing `users` and `creator_warning_logs`. It is live and executable but recent rows show no current direct/manual use; classify it as **manual capability, recently dormant**.
  3. `BlockCreatorController` writes legacy `creator_warnings` plus the newer user/log fields for its give-warning action. It has no current menu entry, but its direct routes remain executable. Production has only two warning rows, both on 2026-05-26; classify it as **legacy/manual, historically used, still exposed**.
- Exact production evidence: `moderation_warnings` has 1,358 rows with entries through 2026-07-14; `creator_warning_logs` has 58 rows (41 L1 moderation, 9 L2 moderation, 7 L3 moderation, 1 L4 moderation, plus four older manual rows); `creator_warnings` has two warning rows from 2026-05-26 and no block row.
- All warning/moderation controllers, the every-minute auto-unblock command, web routes, and the drift-prone live menu exactly match the audited files on app-1, app-2, and app-3. The live API/AuthController is identical across all three nodes; production remains authoritative over the differing Git file.

### Android/API warning display

- The active JWT-protected `my_warnings` endpoint correctly binds body `user_id` to the JWT subject. Female creator history comes from `creator_warning_logs`; male moderation history comes from `moderation_warnings`. This is a notable exception to the many body-ID API failures elsewhere.
- The endpoint loads each user's complete warning history without pagination. Current histories are tiny, and `creator_warning_logs.creator_user_id` plus `moderation_warnings(creator_user_id, consumed, severity)` keep the per-user reads selective, though both paths filesort for their requested order.
- `MyWarningsActivity` is the current Android renderer. On any API/network failure it deliberately falls back to the empty “All Good” state with no error toast. A suspended or warned account can therefore be shown as clean during an outage, auth problem, or server error.
- OneSignal click routing recognizes `creator_warning` and `block` and opens `MyWarningsActivity`. The legacy give-warning payload uses type `warning`, and male moderation uses `user_warning`; neither has an explicit Android click branch, so those notifications do not reliably deep-link to the warning screen.
- No `creator_warning_image` setting is currently configured. The upload feature is therefore latent. If used, it writes the file only to the load-balanced node handling the request while storing one global path; other nodes can return no image and a later load-balanced asset request can 404. This follows the already-proven asymmetric media topology.

### Active moderator policy and destructive side effects

- Moderator escalation identifies a person by matching creator/user names to a call near an incident date/time, or accepts hidden confirmed IDs after an ambiguity selection. At level 0, 3 Normal / 2 Medium / 1 High unconsumed incidents trigger Level 1; each later creator incident raises one level through permanent Level 4. Male users cap at Level 3 and are never account-blocked.
- Creator Level 4 through moderation sets `blocked=1`, disables audio/video, creates a permanent warning block (`warning_block_until=NULL`), appends the warning log, sends a warning, then sends FCM `clear_data` and replaces the stored FCM token with `0`.
- Every successful creator or male level-up hard-deletes the person's entire chat history: messages where they are sender/receiver, both participants' active-chat entries for discovered conversations, their reactions, and conversation headers. This is an irreversible high-impact side effect of a warning action, not a separate “delete chat” operation.
- The 10.3M-row message delete can use an index-merge union of `from_user_id` and `to_user_id`, and active-chat/chat/reaction cleanup columns are indexed. It is chunked by 5,000 messages, but the overall warning action is not transactional.
- Level update, warning-log insert, provider send, chat deletion, count consumption, and optional token invalidation are not one transaction and do not lock the user/counter rows. A failure after the user level changes can return an error with only part of the side effects complete; staff retry can then advance the next level and repeat deletion/push work. Concurrent moderators can also race threshold counts or level reads.
- Chat deletion catches failures and continues, so partial deletion is an accepted outcome. This cross-links to Checkpoint 05: a moderation warning can remove histories for both participants while leaving partial list/reaction state if a later cleanup step fails.

### General Creator Warnings inconsistencies

- The page is search-only and caps matched creators at 50, preventing the previous all-creator aggregation. Search resolves IDs first and scopes 30-day rating/call-drop calculations. Without a search term it intentionally returns no creators.
- Its routes have no role-level middleware or controller support guard. Role 3/4 are blocked by global middleware, but support role 2 sees the menu and can upload the shared warning image, change any verified female creator's warning level/restrictions, and trigger outward warning/clear-data notifications.
- Warning level is only allowed to stay equal or increase; it can never decrease. The code that “resets to Level 0” and deletes history is unreachable for any creator already above zero. A warned or banned creator cannot be rehabilitated from this page.
- Direct Level 4 is defective: the block logic only handles optional Level 2/3 toggles. At Level 4 the `else` branch can clear warning-specific blocking and does not set `blocked=1` or disable availability; it only sends the ban notification and FCM clear-data/token reset. A creator can therefore be labeled permanently banned without the server-side call/account block applied by the moderator engine.
- Equal-level edits are allowed and can remove a current call block or withdrawal hold while leaving the warning level unchanged. Updates, history inserts, provider calls, and token invalidation are not transactional or row-locked.
- The controller has an all-creators CSV export implementation, but no deployed route or Blade caller reaches it. Classify that method as dead/unreferenced, not an active export.

### Legacy Block Creator inconsistencies

- Give Warning uses a separate five-level policy: L1 monitor; L2 1h block; L3 4h; L4 24h plus 7-day withdrawal hold; L5 indefinite call block. Android/API warning titles only define levels 0–4, so Level 5 displays as “Unknown” even though details exist. The general warning page cannot lower or edit a Level-5 creator because its validator only accepts 0–4.
- Its five-level details say Level 5 pauses calls and withdrawals indefinitely, but executable code gives the withdrawal hold a seven-day end. The indefinite call block remains because `warning_block_until` is null and the auto-unblock command only selects non-null expiries.
- A legacy block record is historical rather than stateful: `isCreatorBlocked()` returns true forever if any block row exists, even after the user's live `blocked` flag is cleared. Toggle/unblock does not close or supersede that record.
- Legacy `blockCreator` and toggle routes change `users.blocked` but do not set `manually_blocked`. If the creator also has a temporary warning block, the expiry command can later clear `blocked` and unintentionally undo that separate manual block.
- Support role 2 is denied from the legacy mutate methods in-controller, but the search route lacks that guard. The page has no live menu entry, limiting normal discoverability without removing direct URL reachability.

### Enforcement and expiry

- `users.blocked=1`, not the warning label, is the main call gate. It prevents availability from being enabled, blocks male-to-female and female-to-male call setup, blocks random calls, and blocks both bank and dormant UPI withdrawals. Several messages incorrectly hard-code “48 hours” regardless of actual warning duration or permanent status.
- Bank withdrawal additionally calls `validateWarningWithdrawalSuspension`, so a withdrawal-only Level-3 restriction is enforced even without `blocked=1`. The dormant UPI withdrawal path omits this warning-specific check; if UPI is re-enabled, a withdrawal-only hold can be bypassed unless the account is also blocked.
- `creators:auto-unblock-warning` is genuinely scheduled every minute on both app-1 and app-2 with node-local overlap locks. It clears expired warning call/withdrawal flags and `blocked` unless `manually_blocked=1`, but deliberately leaves audio/video off until the creator re-enables them.
- The dual scheduler executions are mostly idempotent, but there is no row lock/version. A command can load an expired creator, race an admin applying a new restriction, and save clearing the newly extended block/hold. The two scheduler nodes increase that race window.
- Snapshot state: 1,563,054 users at warning level 0, 32 at L1, 3 at L2, 6 at L3, and 1 at L4. The one L4 user is blocked with both availability flags off. There were no current `warning_withdrawal_disabled=1` rows and only the permanent L4 warning block (`until` null) at the read-only snapshot.

### Other account-block admin conflict

- `BlockedUsersController` is managing pair-block rows but its bulk action also writes the selected `call_user_id` into the global `users.blocked` account flag. Bulk unblock sets it to zero without considering permanent warning blocks, manual blocks, or other selected pair rows. It can therefore unban a moderation-banned creator; bulk block can globally suspend someone merely because a pair row was selected.
- The Blocked Users menu is hidden from support, but its routes have no role-level/support middleware and the controller has no authorization guard. Support role 2 can invoke the bulk write directly. This is an active authorization/state-integrity risk even though menu presentation suggests otherwise.

## Tickets, public support, and AI replies

### Proven callers and runtime classification

- Android's normal support surface is active. Both profile variants open `HelpAndSupportActivity`; both can view ticket history. The male flow exposes Raise New Ticket directly, while the female flow reaches submission through support categories and Other Queries. `SubmitTicketActivity` requires a message of at least 15 characters, allows up to three screenshots, disables its button while a request is pending, and calls the authenticated multipart `create_ticket` API.
- Android calls the `/api/auth/` variants of `create_ticket` and `tickets_list`. The same two methods are also registered at the API root outside the route middleware group, but each method performs its own `auth('api')->user()` check; both URL variants therefore require a valid JWT in current live code.
- `create_ticket_by_mobile` and `tickets_by_mobile_status` are separately registered as unauthenticated GET-or-POST endpoints and contain no controller authentication. The public `/raise-tickets` GET/POST web form is also unauthenticated. These are **active exposed capabilities** even though no current Android caller was found.
- The normal create path performs AI generation inline in the HTTP request. The scheduled "delayed" command is not the normal producer. `ai:generate-missing-replies` is auto-discovered as an Artisan command but has no scheduler entry or application caller; classify it as **manual/backfill capability**.
- AI Tickets has live direct routes and JavaScript callers for single generation, bulk generation, and provider connection testing. It has no live sidebar link, while the normal Tickets page does. Treat AI Tickets as **authenticated admin capability hidden from normal menu discovery**, not dead code. The GET connection-test route makes a real external provider request and was not invoked during this audit.

### Cross-account and public disclosure failures

- `create_ticket` validates that some JWT exists but never requires body `user_id` to equal the JWT subject. Any authenticated account can create tickets and upload screenshots under another user.
- `tickets_list` has the same ownership failure. Any authenticated account can retrieve another user's complete unpaginated ticket history, including messages, human and AI replies, escalation reason/state, reply-image URLs, screenshot URLs, and timestamps.
- `create_ticket_by_mobile` publicly creates a ticket for the first row matching any supplied mobile number. `tickets_by_mobile_status` publicly returns full messages, replies, reply-image URLs, screenshot URLs, and timestamps from only a mobile number and status. GET support places the mobile/message in URLs and intermediary logs. This is a critical unauthenticated support-history/PII disclosure and impersonation path.
- The public web form also accepts only a mobile number as identity proof, then creates a ticket and up to three public screenshots. It has no authentication, CAPTCHA, ownership proof, explicit rate limiter, unresolved-escalation guard, or AI/escalation flow.
- Live `users.mobile` has an index but is not unique: 1,563,156 populated rows represent 1,560,952 distinct values. There are 1,575 duplicated mobile values, 2,204 extra accounts on those values, and as many as five accounts on one value. Every public/mobile ticket method uses unordered `first()`, so duplicate-mobile ambiguity is confirmed production behavior.

### Inline AI creation behavior

- Normal authenticated creation saves the ticket before contacting OpenRouter. It builds up to five prior-ticket context rows and applies "once manual, always manual," first-redirect money/block categories, second-redirect follow-up categories, sensitive-issue handling, and a follow-up counter. An unresolved manual-escalation ticket blocks another normal authenticated creation, but public/mobile/web creation bypasses that rule.
- If not escalated, the request calls OpenRouter synchronously. A successful AI result is written immediately to both `reply` and `ai_reply`; `needs_human_action` keeps status active, otherwise status becomes resolved. `TicketNotifier` then sends a best-effort OneSignal push in the same request. There is no intended two-minute delay on this path.
- The provider has a 45-second cURL timeout and two retries, with 2- and 4-second sleeps. Worst-case provider waiting is roughly 141 seconds plus database/application work. Because the ticket is saved first and there is no request idempotency key, a proxy/client timeout followed by retry can create duplicate tickets. Android prevents a second tap only while the current process/request remains pending; it re-enables after failure.
- AI/provider failure does not roll back the ticket; it leaves an active unanswered row and still returns ticket-created success if control returns to the controller. OneSignal happens after the database save and has no durable retry/notification outbox, so a visible reply can exist without its notification.
- Production is configured for OpenRouter model `google/gemini-2.5-flash`. Recent database state proves AI reply generation is active: 30,694 of 51,646 tickets had both `ai_reply` and user-visible `reply` at the snapshot, including 131 tickets on 2026-07-14.

### Enabled account-context privacy and performance path

- Live production contains an `AuthController` hand patch absent from the backend checkout. `ticket_ai_account_context` is enabled. Before generating an eligible reply it sends OpenRouter a summary of the user's gender, language, app version, coin balance, withdrawable balance, lifetime income, most recent recharge, most recent withdrawal and reason, seven-day call count, and admin-block state. Follow-up prompts also include recent ticket messages and replies. Screenshots were not included in the examined provider call.
- The provider prompt explicitly labels these as real live account data. Success logging does not log the request prompt, but a non-200/unexpected provider response can log the full response body; invalid summary parsing also logs a response excerpt. User ticket/account facts therefore cross an external AI boundary and model output can enter server logs on error.
- The performance gate measured approximately 73.4M transaction rows, 41.0M call rows, and 611K estimated withdrawals. Transaction and call lookups have usable indexes. The withdrawal lookup `WHERE user_id=? ORDER BY id DESC LIMIT 1` chooses a backward primary-key scan rather than the user index. `EXPLAIN ANALYZE` with a nonexistent user scanned 620,632 rows and took about 1.7 seconds. This cost is in the synchronous create request before the potentially 141-second provider wait.
- For symptoms such as slow/timeout ticket creation, duplicated tickets after retry, or node/request worker exhaustion, check the enabled account-context withdrawal plan and OpenRouter latency first. A user with no withdrawal is the worst case for the current plan.

### Scheduled delayed delivery and stranded rows

- `tickets:send-delayed-replies` is present in all three deployed scheduler source files and runs every minute on the scheduler hosts. It selects only rows with `ai_reply IS NOT NULL`, `reply IS NULL`, and creation age between two and ten minutes.
- Current normal create, AI Tickets single/bulk generation, and manual backfill all write `reply` and `ai_reply` together. No normal current producer intentionally creates the scheduled command's input. Treat it as **legacy/fallback recovery for anomalous rows**, not as the active delivery design.
- The command has no row claim or database lock. `withoutOverlapping` is host-local, so multiple scheduler hosts can select, save, and notify the same row. It also uses `whereDate` for per-user same-day counts and sends OneSignal after the save with weaker provider-success interpretation than `TicketNotifier`.
- The fixed two-to-ten-minute window permanently misses anything older. Production had exactly five `ai_reply`/null-`reply` rows, all created from 2026-02-05 through 2026-02-08; none were currently eligible. These five user replies are stranded unless a manual action changes them. The timezone check explicitly used IST because Laravel timestamps are stored in IST while MySQL `NOW()` returned UTC.
- `ai:generate-missing-replies` selects recent rows with null `ai_reply`, applies controller escalation logic through reflection, and writes both reply fields together. It does not notify users after generating replies and is not scheduled. Running it manually could therefore make replies visible without notification and still cannot repair the five opposite-state anomalies.

### Admin ticket surfaces and authorization

- Tickets, AI Tickets, update, and bulk-status routes are in the broad authenticated/email-verified/2FA admin group with no per-route role level. Global middleware blocks role 3 and role 4, but support role 2 can read all tickets, manually reply/upload images, change statuses, invoke AI generation, bulk-generate replies, and call the external provider connection test by direct URL.

Current size is moderate, but the plan does not scale cleanly.

### Android and notification failure presentation

- Help and Support maps list/API failures to the same "No ticket raised" state. A user can be shown no tickets during auth, network, ownership, or server failures. Combined with the unpaginated response and cross-account body ID, symptoms must be diagnosed from both request identity and response state rather than the empty UI.
- Ticket pushes use data type `your ticket`, which Android recognizes for support navigation. Provider delivery is best-effort; `TicketNotifier` checks for an actual OneSignal ID/errors, while the delayed command treats any successful HTTP response as success and logs provider payload/response details.

### Media storage and schema evidence

- Ticket screenshots use `storage/app/public/tickets`; manual reply images use `storage/app/public/uploads/ticket_replies` and are tracked in `reply_images`. Both are stored on the public disk of whichever load-balanced node handles the upload, so the already-proven asymmetric storage topology makes subsequent asset availability node-dependent.
- Ticket reply updates and ticket deletion did not show a corresponding file cleanup path in the reviewed code, so the DB row and the backing files can diverge. That is the same node-local media problem in a different feature family.
- On Android, `SubmitTicketActivity` copies each selected content URI into deterministic `cacheDir/ticket_image_<index>.jpg` files before Retrofit submission. It clears the URI list after success but never explicitly deletes those cache copies on success, API error, network error, or Activity destruction; cleanup is left to later overwrite or OS cache eviction. Ticket display uses Glide, and the full-screen attachment pager pins both source/transformed data with `DiskCacheStrategy.ALL` without a ticket-delete invalidation hook.
- `tickets.screenshot` is `varchar(191)` while holding either a path or JSON array. At the snapshot, 8,257 rows had screenshots, maximum stored length was 169, none sat at the 191-character limit, no JSON-array row was invalid, and 1,276 rows contained three images. There is no current evidence of truncation, but the schema leaves little headroom and does not solve node replication.
- The table had 51,646 exact rows and about 68 MB total size. Its only secondary index is `user_id`; per-user latest/history requests filesort, and the every-minute delayed-state scan examines the full table. Snapshot states were 626 active, 51,020 resolved, 30,694 AI-delivered, five AI-waiting, 20,273 human-only, 674 unanswered, 11,370 marked manual-support, and 4,196 needing human action.

## Agency portal, assignment, and settlement

### Authentication and authorization boundaries

- Agency login is a public web form that finds the first active agency by `contact_email` and verifies a hashed password. Protected portal methods consistently require `Session::get('agency_id')`; creator detail enforces that the requested creator belongs to that agency. This is a real agency-scoped session boundary, not a route-name convention.
- The login routes have no throttle middleware and successful login does not regenerate the Laravel session ID. Logout is a state-changing GET. The schema does not make `contact_email` unique and creation permits email without password; current live data has no duplicate active email and the one active agency has a password, so those ambiguity/null-password defects are latent today.
- Runtime session storage behind the three-node load balancer remains an explicit uncertainty. No cached Laravel config exists on the nodes, and `.env` was not inspected because it is secret-bearing. Do not assume sessions are shared or node-local without a safe runtime-specific check.
- Internal agency administration does not use the normal admin login, role level, 2FA, or named person. Every `/admin/agency-*` route uses one shared HTTP Basic username/password from environment. Possession of that shared secret grants full creator/KYC/bank/call/withdrawal access, CSV export, agency creation, creator assignment/reassignment, commission mutation, and payment-ledger insertion.
- `AdminBasicAuth` performs constant-time password comparison and fails closed if not configured, but has no per-route throttle and produces no individual admin identity. `recordPayment` stores only `recorded_by='admin'`; create/reassign logs record IP rather than a person. This is a high-impact shared-credential/accountability boundary.

### What the agency can actually see

- Controller comments claiming the agency portal exposes no earnings are stale. Dashboard, creator list/detail, CSV, and settlement views show current balance, lifetime/call earnings, pending withdrawals, last withdrawal history/references, gross/net/commission/paid/pending settlement, and call history. This is executable/rendered behavior.
- Mobile, PAN, and account numbers are masked for agency views/CSV. Creator detail still exposes PAN holder name, bank/branch/IFSC/holder name, masked account, KYC/bank status, last-seen/timeline, up to 200 recent calls, and ten withdrawal entries. Treat these as intentional agency-visible financial/KYC data, not as hidden internal fields.
- Agency routes contain no write operation for creator profile/KYC/bank/calls. Their mutations are limited to login/logout; all assignment, commission, and payment recording are behind the separate Basic-auth admin surface.

### Assignment and withdrawal enforcement

- `users.agency_id` is the membership source. Login/profile APIs expose `withdrawal_blocked=true` whenever it is non-null; Android hides/disables withdrawal, and both active bank and dormant UPI backend withdrawal paths reject agency creators. This cross-links to Checkpoint 06.
- `addCreatorToAgency` enforces female gender and explicit confirmation when moving between agencies. `reassignCreator` does neither: it accepts any user ID and nullable agency and writes directly. Production has 11 assigned users—10 female and one non-female—confirming the unrestricted reassign path has bypassed the female-only design.
- Reassignment is a single user update with no check for pending withdrawals, payout-in-flight state, existing settlement/payment rows, or commission override cleanup. A creator can be blocked from new self-withdrawals immediately while an existing payout/cron/webhook continues independently.
- Search by mobile/name uses unordered first-match semantics against non-unique identities. Search returns the full mobile number to the shared-Basic-auth admin page. Assignment itself uses selected numeric ID, so ambiguity occurs during discovery rather than the final update.

### Settlement calculation and integrity

- Settlement gross is `SUM(user_calls.income)` per creator and date range. Commission is a host override or agency default (code default 10% despite a stale 30% docblock); net is gross minus commission. Recorded `agency_host_payments` are bookkeeping only—no bank/provider transfer occurs.
- Production flag `agency_settle_count_inapp_withdrawals` is disabled. Code therefore uses only manually recorded agency payments to reduce pending; in-app withdrawals are informational. The live shared Blade still says in-app withdrawals “count toward settlement” and defines Covered as recorded payments plus withdrawals. Current UI text is false and can make agencies/admins believe pending was reduced when code did not reduce it.
- Per-host commission lookup filters `agency_host_commissions` only by `user_id`, ignoring its stored `agency_id`. Assignment/reassignment does not delete/update the override. A creator moved to another agency inherits the old agency's host rate until someone explicitly overwrites it. No overrides exist in live data, so this is latent.
- `recordPayment` verifies current agency membership but has no idempotency/unique transfer reference, proof attachment, provider verification, or duplicate check. `paid_on` can be any valid date, and repeated form submissions insert repeated settlement credit. Entries cannot be corrected/deleted through this controller. Production has six records totaling ₹2,030, all dated 2026-06-18, proving the ledger is active.
- Settlement is period-scoped: only payments whose `paid_on` falls inside the selected earnings range cover that range. A later payment for an earlier cycle does not cover the earlier query and instead appears in the later period regardless of which earnings it paid. Advance is inferred arithmetically, not tied to a transfer or cycle.
- Commission writes have no audit ledger/history. Agency default update returns success even if the agency ID does not exist; host update verifies membership and uses user ID as the sole upsert key.

### Query plans and operational failure leads

- Current live scope is small: two agencies (one active), one agency with 11 assigned users, six payments, and no commission overrides. Core settlement call aggregation uses the `call_user_id` index effectively, and settlement correctly casts creator IDs to strings for varchar `withdrawals.user_id`.
- Several admin/detail paths still pass numeric IDs to `withdrawals.user_id`. Live `EXPLAIN` for three numeric IDs chose the status index and estimated 306,970 rows; the same string IDs used the `(user_id,status)` index and estimated three rows. Internal list paid/pending aggregates and creator detail can therefore scan hundreds of thousands of withdrawals despite comments claiming the cast issue was fixed.
- The agencies list joins all paid withdrawals to users and groups by agency. Its live plan also estimates 306,970 paid rows and a temporary result. With only two agencies this remains a full paid-withdrawal scan on every view.
- Internal list sorting by total paid/call count occurs after pagination, so it sorts only the visible 50-row page, not the full agency population. Labels such as “Most Paid” are not global rankings.
- Agency creator CSV loads all agency users and grouped financial/call data into memory before streaming. The current 11-user scope is safe; a large future agency/all-agency export can become memory/latency heavy.

### Live-source equality

- `AgencyDashboardController`, `AgencySettlementController`, `AdminBasicAuth`, and `routes/web.php` exactly match Git and each other across all three nodes. The shared-Basic boundary, unthrottled agency routes, financial exposure, and settlement behavior are live code, not repository-only assumptions.

## Admin authentication, 2FA, role boundaries, MCP access, and outward operations

### Normal web login and the real role gate

- The executable admin login is `Auth\\AuthenticatedSessionController` through `routes/auth.php`; the imported legacy `LoginController` is not the routed login. It rate-limits failed credentials to 30 attempts per lowercased email per roughly one minute, calls `Auth::attempt`, regenerates the session on success, rejects `is_active=0` and `is_disable=0`, records role-1/2 login metadata, updates `last_login`, and fully invalidates the current session on logout.
- `is_login_enable` is not checked by this normal login, although other code treats it as a login-disable control. The registered `admin_staff/{id}/toggle-active` route points to a nonexistent `AdminStaffController::toggleActive` method, so that advertised toggle is broken at dispatch. Password changes correctly require the current password and update the authenticated admin only, but do not explicitly revoke remember tokens, other sessions, or MCP tokens.
- The broad admin surface is `verified` + `twofactor`, with individual pages commonly adding `auth`/`XSS`. `Admin` does **not** implement Laravel's `MustVerifyEmail` contract, so `EnsureEmailIsVerified` passes every admin regardless of `email_verified_at`. The route-group name gives false assurance: live production has only five of 34 admin rows email-verified, yet verification is not an effective access condition.
- Global web middleware gives real allow-list enforcement to role 3 (view-only) and role 4 (moderator). Role 3 is limited to safe-method dashboard/report routes plus 2FA/logout; role 4 is restricted to moderation warnings plus 2FA/logout and redirected away from other safe pages. The view-only middleware's comments claim own-account update is allowed, but its GET-only rule blocks the POST account/password actions.
- The support restriction middleware is registered as `check_support_staff` but is attached to no route. Role 2 therefore receives the entire broad verified+2FA route group unless a route or controller separately rejects it. Sidebar `@if` hiding is frequently the only distinction and is not authorization. The live sidebar currently matches Git and all three nodes, but that does not repair direct URL access.
- Production has 34 admin accounts: 18 role 0, one role 1, 12 role 2, two role 3, and one role 4. All were active and had `is_disable=1` at the snapshot. Login logging covers only role 1/2 by design: 97 role-1 and 3,587 role-2 entries existed; role 0/3/4 logins are absent from that audit table.

### Mandatory TOTP behavior and weaknesses

- Web 2FA is genuinely mandatory for the broad group. Unenrolled accounts are redirected to setup; enrolled accounts need a session `2fa_passed` flag. Verification accepts a six-digit TOTP in the previous/current/next 30-second window and POST verification is throttled to ten requests per minute. Logout invalidates the session, clearing the flag.
- Enrollment routes require only an authenticated password session and deliberately bypass the 2FA gate. `two_factor_enroll_allowed=1` permits setup even when 2FA is already enabled; successful setup overwrites the stored secret and marks the session passed. Live state contains one enabled account that still has enrollment permission. A password-only attacker for that account can therefore replace its existing TOTP without knowing the old code.
- All six currently unenrolled accounts are allowed to enroll. This is operationally necessary for rollout but means stolen credentials can bind the attacker's authenticator before the owner enrolls. The shipped `admin:2fa-lock` control has not closed that window for those rows.
- TOTP secrets are stored as plaintext `varchar(64)` values. `Admin` has no encrypted cast and the controller reads/writes the raw value. There were no enabled-with-null or disabled-with-secret inconsistencies at the snapshot, but database/read access exposes reusable second factors.
- Current enrollment is partial: 21 of 34 accounts have 2FA enabled (13/18 role 0, 0/1 role 1, 6/12 role 2, 1/2 role 3, and 1/1 role 4). The normal mandatory redirect protects web-panel use after login; it does not protect the separate MCP password flow.

### MCP password login is an alternate privileged security boundary

- Public `/mcp-login` validates only admin email/password behind a 10-per-minute IP throttle. It does not require web 2FA, email verification, or an existing admin session. It checks `is_active` and `is_login_enable` but omits the normal login's `is_disable` check.
- Role mapping is stored into the newly minted token: role 0/1 becomes `superadmin`, role 2 becomes language-scoped `support`, role 3 becomes `view_only`, and every other level falls through to `support`. Consequently the live role-4 moderator—whose web access is intentionally moderation-only—can use password alone to mint a support MCP token with creator approval/rejection, ticket reply/AI generation, user coin credits, payout/coin refunds within caps, withdrawal cancellation, chat deletion, notification send, profile mutation, and moderation-write capabilities.
- Superadmin MCP access includes guarded high-impact writes and a raw database endpoint. The DB endpoint itself is SELECT/SHOW/DESCRIBE/EXPLAIN-only with statement filtering, one-statement enforcement, a 10-second limit, and result caps; the token still grants many separate balance, withdrawal, gender, block, config, and moderation mutation endpoints.
- A self-service login revokes prior active tokens for that linked admin and creates a 90-day SHA-256-hashed bearer token. The operation is not transactional. The page's “logout” only forgets the one-shot plaintext from the browser session; it does not revoke the copied bearer token. Account password/role/status changes are also not consulted by `McpTokenMiddleware` after issuance: it trusts the token's stored role until revoked/expired.
- Strong review on 2026-07-15 found a live MCP budget-reporting defect on all three nodes. `McpAuthorizes::remainingBudgetToday()` calculates `payout_count_remaining` from `$token->daily_payout_count`, but production `mcp_tokens` has `daily_payout_cap_rupees` and no `daily_payout_count` column or model accessor. Consequently `/api/mcp/auth/session`, `/api/mcp/refunds/budget`, and `mcp:budget` report zero payout-count remaining even when the token's shared count allowance is unused. The authoritative payout transaction does **not** use this missing field: `RefundsMcpController::executePayoutRefund()` locks the daily usage row and enforces payout count against `daily_refund_cap_count`, so this is currently misleading diagnostics rather than a cap bypass. `canIssuePayoutRefund()` would incorrectly reject a sub-threshold support payout as count-exhausted, but no executable caller of that preflight helper was found. The five reviewed MCP source files matched byte-for-byte across app-1, app-2, app-3, and the local backend; a bounded production schema query confirmed the missing column.
- Production has 96 MCP token rows and 17 currently active/unexpired tokens. Fourteen active tokens have no expiry. Two are unlinked, non-expiring `superadmin` tokens, so no admin login can revoke them through the one-token-per-admin behavior. Among linked active tokens, one role-0 account currently holds a stored `support` token rather than its derived role; stored role drift is real, not theoretical.
- MCP is actively used: the audit log includes 4,221 successful ticket views, 3,129 ticket replies, 843 successful raw DB queries, 742 user-activity reads, 166 creator approvals, 99 rejections, 15 coin refunds, and other operations through July 2026. This is an operational admin plane, not dormant tooling.
- Recheck on 2026-07-15 confirmed the current code still matches this security picture: `AdminStaffController` still lacks `toggleActive`, `check_support_staff` remains registered but unattached, `AdminBasicAuth` still relies on the shared env secret, and MCP logout still clears only the browser session rather than revoking the bearer token.

### Support/direct-route outward and high-impact operations

- Immediate broadcast notifications, custom segmented notifications, scheduled screen-notification CRUD/AI generation, personal notifications, Smart Notification toggle/manual run, settings/cache actions, daily reports, AI monitors, WhatsApp campaign imports, and many content/config resources sit in the broad role-0/1/2 group with no controller role check. The sidebar hides several from support, but role 2 can invoke them directly.
- `NotificationsController::store` saves a campaign and immediately calls OneSignal. `CustomNotificationController::send` resolves the selected audience, writes tracking state, and calls OneSignal in batches. - Scheduled Notifications is intentionally visible to support. Its rows are not merely content drafts: the public every-minute `cron_jobs` method reads due rows and sends them via OneSignal filters or explicit user batches. Production has 139 rows from 2026-06-19 through 2026-07-07. Its per-minute duplicate lock uses Laravel cache; earlier infrastructure evidence shows scheduler/cache ownership is multi-node, so node-local/shared-cache behavior remains part of duplicate diagnosis.
- Smart Notifications is scheduled at fixed daily times and production's node-local `DISABLE_SMART_NOTIFICATIONS` file is absent on all three nodes, so it is enabled. Any role 0/1/2 direct caller can create/delete that flag only on the load-balanced node handling the request or execute the notification command inline. A toggle can therefore disagree across nodes; manual run can send outward and returns command output to the caller.
- The old broadcast `notifications` table has 397 rows but stops at 2026-04-05. Trackable custom notifications show one 38,603-recipient send on 2026-06-23. ## Cached report APIs: public execution does not equal proven use

### Reachability, caller evidence, throttling, and cache topology

- The live route file exposes paid-registration, revenue, call-connection, user/creator D7 retention, four ticket-quality, installs, ROAS, and register-to-purchase feeds without authentication. Only `users-report` checks a bearer-style secret inside its controller. `cache.reports` caches successful GET responses for ten minutes.
- A repository-wide caller search found no executable local caller. Searches of retained HIMA app/report access-log families and the separate `/var/www/hima_analytics` and `/var/www/hima_base` source trees found no calls to these endpoint names. The separate `hima_reports` nginx vhost serves `/var/www/hima_analytics` and does not itself prove it consumes the Laravel feeds. Treat the endpoints as **publicly executable with current polling/runtime use unproven**; comments claiming a sheet/dashboard polls every two minutes are not runtime evidence.
- Global API throttling is effectively absent: the deployed `api` limiter permits 60,000 requests per minute per authenticated user or IP. This exact provider source matches Git and all three nodes.
- The outer response-cache key uses the raw path/query string and raw Authorization header. Public endpoints ignore arbitrary Authorization values and unused query parameters, so either can create unlimited cache misses for the same expensive computation. `Cache::remember` inside per-day endpoints also has no cross-request computation lock, allowing a cold-key stampede.
- All nodes use Laravel Redis cache with the same database number and prefix. The configured host strings differ—app-1 uses a local address while app-2/app-3 use the primary's private address—but final read-only Redis `run_id` fingerprints prove all three reach the same Redis server. There are not two cache partitions. Cold misses can still dogpile because the report compute/write sequence has no claim lock, and arbitrary cache-key-varying inputs create distinct cold keys.

### Users report and paid/revenue feeds

- `users-report` is token-gated and the cache key includes the Authorization header, so a successful cached response is not served to a tokenless caller. It still mixes replica and primary reads in one response: registrations and all language breakdowns use the replica, while several headline recharge/paid/verified values use primary. Replication lag can make language rows fail to reconcile to headline totals despite comments claiming they sum exactly.
- “Verified creators” means `verified_datetime IS NOT NULL` on female signups. Earlier creator auditing proved bulk pending/rejected changes also write that timestamp, so this is not a reliable current-approved count. “New users first purchase” counts distinct same-day registered male payers, while Day-0 revenue sums every same-day recharge they made, not only each user's first transaction.
- Public `paid-registered-by-language` has no maximum range, does not allow-list gender, uses `DATE()` on transaction/user timestamps, and has no internal per-day cache. A representative one-day `EXPLAIN` estimated 5.15M `add_coins` transaction index rows, temporary table, and filesort. Its outer cache is trivially bypassed with an unused query parameter/header.
- Public revenue-by-language is better bounded to 93 days and uses an index-friendly per-day transaction range; the one-day plan estimated about 26K rows. It reports paying-user-days, not unique payers over the window, and says so in its payload. Up to 93 separate cold day computations can still stampede and run independently on the two Redis backends.

### Calls and D7 retention

- Public call connection permits a 93-day window but computes each cold day as 24 sequential hourly queries—up to 2,232 queries. A representative hour estimated about 40K call rows, roughly one million per day. The method itself warns cold windows over two days can exceed nginx timeout, yet leaves the much larger public bound executable.
- Its “connected” signal is still `(income > 0 OR coins_spend > 0)`, not transport/media connection truth. Free connected calls are excluded; financially touched anomalous rows can be included.
- User D7 is a two-day D+7/D+8 window and treats any appearance in calls on either side—including an unanswered inbound ring—as retained. Default `auto_shift=1` silently replaces too-recent requested dates with an older window. For each cohort user it runs up to two correlated call lookups; a representative day estimated about 5.7K users with roughly 148/265 candidate call rows per dependent lookup.
- Creator D7 uses all female registrations as the creator cohort, not verified/approved creators, and the same money-moved proxy for a connected received call. Its stricter signal is better than any-ring retention but its denominator still includes rejected/pending/noncreator female accounts.

### Marketing KPIs are not ad-platform ground truth

- `installs` counts unique rows in `user_install_referrer_responses` whose client-supplied referrer resembles Meta/Google paid traffic. The current Android app copies the saved referrer into that table only for logged-in **male** users; female creator installs never enter this KPI table through the audited caller. It is therefore registered-male paid-referrer attribution, not total installs.
- The user-referrer producer is public, trusts an arbitrary `user_id` and response body, and the table has a unique user key. A caller can claim/poison another user's one allowed attribution before the legitimate app. The KPI's source classification and region are therefore forgeable/current-profile data, not independently verified ad-network evidence. The representative one-day plan was bounded at about 6K rows but scans raw response text for Google markers.
- `roas` does not select paid-acquired users and contains no ad spend. It sums 30-day recharge revenue for **all** users registered each day; a caller must divide by external spend, but even then organic and other acquisition cohorts remain in the numerator. Recent cohorts are partial. The representative plan was indexed but joined about 4.3K daily users to an estimated 52 transaction rows per user.
- Register-to-purchase is a reasonable all-user signup conversion measure, not specifically a marketing/ad cohort. It evaluates a dependent recharge existence query for each daily signup and allows 93 cold daily cohorts. A representative day estimated 5.7K users and 52 candidate transaction rows per user; recent cohorts are correctly labeled partial.

### Ticket-quality feeds conflate states and timestamps

- All four ticket feeds are public. `tickets` has only a user-ID secondary index, so representative date-window plans scan the whole roughly 45–52K-row table; reopen also performs a per-row indexed user subquery. Current scale is moderate, but random cache keys can force repeated full scans/PHP aggregation.
- “Resolution rate” does not require a reply, status 1, or any resolved marker. It labels every `escalated_at IS NULL` ticket auto-resolved, including unanswered/non-escalated tickets, and publicly returns top escalation-reason text. It measures non-escalation share, not resolution.
- First-response time and resolution time use the exact same mutable timestamp difference: `updated_at - created_at`. Later status/bulk edits can change `updated_at`; no immutable first-response/final-resolution timestamps exist. The two feeds differ mainly by SLA threshold/status predicate, not by distinct lifecycle events.
- Their business-hours helper counts 10:00–18:00 IST on all seven calendar days and ignores holidays. Region/language filters are applied in PHP after fetching/calculating all qualifying rows, so narrower filters do not reduce DB/PHP work.
- Reopen rate requires a nonempty reply but not resolved status and calls any later ticket from the same user within N days a reopen, regardless of issue/category. Recent cohorts are not held until the entire forward window matures, so their rate is structurally depressed. It is a broad repeat-contact proxy, not a same-problem reopen or defensible CSAT measurement.

### Source and optimizer proof

- `UsersController`, `CacheReportResponses`, `RouteServiceProvider`, and `config/cache.php` match Git and all three nodes. Public routing was checked from the live drifted `routes/api.php`. Production schema/optimizer evidence was collected through information-schema and `EXPLAIN` only; no analytical endpoint or large SELECT was executed.

### What data crosses the provider boundary

- Start sends OpenRouter the user's cleaned name, concern, language, and up to ten recent in-app chat snippets involving the user. Those snippets include both the user's text and the other participant's text, truncated to 120 characters each. ### Delivery behavior and likely bug causes

- Start's recent unfinished-session lookup is unordered and has no unique key/transaction, so concurrent starts can delete/recreate or select an arbitrary eligible session. Bugs described as “message exists but creator did not see it live/get notified” therefore have a direct architectural cause.

Android's delivery cards instead preview a separately hardcoded concern/language template. The user can be shown a sentence as “sent” that is not the sentence stored for any creator.
- `get_user_concern` is not a creator/peer lookup in executable code: it binds the JWT subject and searches that same user's session. No caller exists in the current Android tree. Treat it as an unused, purpose-broken endpoint rather than evidence that creators receive onboarding context.

### Delivery selection and recurrence defects

- For non-segment rows, candidates are shuffled and only the first row for a gender/language combination is sent in a minute; which authored notification wins is nondeterministic. There is one current duplicate gender/language/time/day slot, so one of those two rows is skipped unpredictably on each execution.
- Segment rows do not honor the advertised same-slot dedupe. The pre-check looks for `gender_language`, but a successful segment path records `segment_<segment_key>` in the in-memory array. Another segment row with the same gender/language still passes. Its collapse ID also includes notification ID and batch number, so OneSignal does not collapse competing rows together.
- Segment selection materializes full user-ID arrays in PHP, optionally feeds them through a large `WHERE IN`, then sends 2,000 IDs per request. Retained examples reached 44,734 and 53,960 recipients in one schedule. Several segment definitions perform 7–90-day call/transaction existence or grouped scans; the admin preview GET and minute cron can repeat the same expensive query without a result cache.
- The code records no durable send-attempt/success row for this schedule family. Successful/failure knowledge lives only in rotating application logs. Segment code logs a summary after all batches even if some fail; there is no retry queue for failed batches, and non-segment failures also wait until the next matching week/time rather than retrying.

### Media and edit defects

- New logo/image uploads use node-local `storage/app/public`. Delivery constructs URLs as `/storage/app/public/<path>` rather than the normal public-storage symlink URL, and no shared-media layer is present. Current rows have no media, so this URL defect is latent for the live schedule snapshot.
- Update deletes the old stored file and writes the new one into an undefined `$validated` array, but never persists that new path to the model. The database retains the old now-deleted path while the new file becomes orphaned. Delete/bulk-delete similarly remove files only from the handling node.
- `ScreenNotificationsController`, `SegmentService`, the model, and the relevant route block match live on all three nodes. Whole `OpenRouterService` and local `routes/web.php` differ because of unrelated live/local drift, but content hashes of `generateNotifications`, `buildNotificationPrompt`, and the screen-notification route block match live exactly. These conclusions isolate executable code from unrelated changes.

## Exports, invoices, and imports: executable paths versus labels

### Users Reports CSV: actively exercised and abort-prone

### Transaction invoice PDF and GSTR CSV: executable but inconsistent

- Single invoice download, bulk PDF, and GSTR CSV are real controller methods. The menu hides the bulk form/payments from support, but the routes remain in the broad group without a role-level guard, so role 2 can call them directly. No current retained access hit was found.

It logs “completed successfully” before the response callback actually executes, so the log can claim success even if streaming later fails.

Invoice generation therefore has an unnecessary outward/network dependency and can fail or stall on DNS/TLS/HTTP availability.
